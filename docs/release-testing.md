# 上线前回归测试

回归分为源码、原生能力和安装后流程。自动测试通过代表这些已声明场景在当前提交和平台通过；不代表真实网站、供应商、系统授权、更新包或长期运行的所有组合都已验证。

## 一键检查

安装开发依赖与本平台原生构建依赖后运行：

```sh
npm run test:release
```

默认顺序执行全部前端测试、CLI 类型约束、完整类型检查、生产前端构建、Rust 库与 CLI 测试、原生 CLI 构建，以及隔离目录中的 Skill 安装与升级。任一步失败都会以非零退出码结束，后续步骤不会运行。

可分别执行：

```sh
npm run test:release -- --phase frontend
npm run test:release -- --phase native --output output/release-native
# 先构建本机安装包。默认连接已经运行的软件；--start 允许通过 CLI 启动。
npm run test:release -- --phase desktop --start --cli /绝对路径/安装包内/zerror-cli --output output/release-desktop
```

Windows CLI 文件为 `zerror-cli.exe`；macOS 在 `ZError.app/Contents/MacOS/`；Linux 在打包目录或解包后的 AppImage 内。CI 先安装 Windows x64 NSIS、复制 macOS arm64 DMG 内的 App、安装 Linux x64 deb，再使用实际安装目录的 CLI。Linux 另外运行 AppImage 的 CLI 启动入口。Linux 图形流程通过 Xvfb 和 D-Bus 执行，不在无显示环境里假装通过。

`--release` 和 `--target <Rust target>` 用于核对 CI 正式构建。`--cli` 始终应指向待验包内的 CLI。不要用开发服务的成功代替正式包的验证。

## 功能测试集

[scripts/release/features.json](../scripts/release/features.json) 记录功能与测试的对应关系：

| 功能 | 自动回归的证据 |
| --- | --- |
| 设置与模型配置 | 共享写入队列、并发修改恢复、设置界面操作、读回与持久化 |
| 数据导入导出与练习 | CSV / XLSX / TXT 二进制往返、引号与多行保护、损坏输入拒绝、评分和纠错统计 |
| 校园题库 | 课程接口、上传与编辑权限、登录关联契约；真实服务另外实机验收 |
| 题库与答题查询 | 查询/搜索协议；原生题目与文件夹增删改查、分页及删除确认 |
| Agent | 模型协议与流式输出、失败恢复、审批、完成判断、任务 ID 隔离、停止 |
| 浏览器 | 定位与观察、导航、输入、媒体控制、iframe；原生输入和子 iframe 点击后读回 |
| 网站经验 | Open 包解析/安装/更新、资源哈希、来源隔离、权限、沙箱与恢复契约 |
| 账号与安全 | 凭据引用、脱敏、授权拒绝；原生临时账号写入与不可读取明文 |
| 本地 HTTP 服务 | 启动、实际 HTTP 健康响应、无效请求拒绝、停止后状态 |
| 导航与工作区 | 导航入口、文件夹、对话、浏览器侧栏及已有 UI 回归 |
| 更新 | 签名更新与普通安装包的决策、重复点击保护、失败状态和重启调用契约 |
| 展示与资源 | Mermaid/D2、Markdown 资源、生产构建及完整类型检查 |
| CLI 和外部 Skill | 参数校验、连接隔离、准确任务等待；真实进程的安装、升级、本地修改保护和离线恢复 |

已有测试全部执行，不仅运行表中少数冒烟用例。功能清单引用的测试被删除、重命名、过滤或没有断言时，校验失败；跳过、todo、pending 和失败测试也不能算通过。这里的“覆盖”是场景证据，不是代码覆盖率百分比。

## 安装后的实际流程

`scripts/test-cli-installed.mjs` 通过真实 CLI → 本地 RPC → 主 Webview → 数据库、凭据存储、Agent 和原生浏览器执行。模型和网页均来自临时本地 HTTP 夹具，不调用收费模型，也不提交真实网站作业。

测试账号域名和记录使用唯一标识；只删除自己创建的记录。结束时关闭自己启动的题库服务，恢复原主题、网络端口、局域网开关和 Agent 模型选择，清理临时供应商、对话、题目、文件夹和账号，并读回核对恢复结果。已有运行中的题库服务不会被停止。不要与用户同时操作设置；测试运行期间需要保持图形会话和原生凭据存储可用。

测试不会执行真实软件升级、卸载、系统授权绕过、无限时内存压力，或真实网站登录与提交。这些项目保留为明确的实机验收项；网站业务还需各自 Open 仓库的测试，桌面端不重新内置平台专用脚本。

## 发布阻断与报告

- `release-checks.yml` 在三种桌面系统运行全部前端功能测试、类型检查和构建。
- `build-desktop.yml` 构建后运行该平台全部 Rust 测试、Skill 进程集成及桌面实际流程。失败就不能上传该平台作为发布输入的安装包。
- `release-desktop.yml` 的签名任务同时依赖功能回归与三平台构建成功；发布依赖签名验证成功。不能用另一个提交或上次运行的成功代替本次结果。
- 每阶段生成 `report.json`、测试日志和前端 `vitest.json`，CI 无论通过或失败都上传回归证据，保留 14 天。

默认报告位于 `output/release-checks/`。每个功能包含实际执行过的测试文件，报告保留本阶段和平台；只运行 frontend 不会宣称桌面安装后流程已通过。

## 发版前实机验收

以下清单也在机器可读报告的 `manualChecks` 中显示，不会伪装成自动通过：

1. 三平台首次安装、覆盖安装、旧数据迁移、卸载和重装。
2. 使用真实签名更新包，从旧版点击更新并重启，核对版本、用户数据、更新失败后的可用性；包括 macOS。
3. 系统凭据授权允许/取消/拒绝，Windows SmartScreen/权限提示，Linux polkit 取消和 AppImage 原包重启。
4. 真实网站仓库的登录、验证码、播放、自动下一节与作答流程；只在用户授权的测试账号和课程中执行。
5. PDF/PPT/图书导入导出、校园题库远程服务、供应商连接，以及拖拽、缩放、主题和多显示器。
6. 长时间浏览、媒体播放、对话与窗口反复开关，检查内存趋势；短时进程测试不能证明没有泄漏。

执行本地验证不触发发版。源码检查可重复运行；桌面流程的外部依赖失败也应报告失败，不能通过加重试或跳过把结果变绿。
